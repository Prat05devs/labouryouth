# Implementation decisions and open release inputs
The user-provided specification is authoritative. This log resolves implementation details without adding features.

1. Headcount: capacity is `headcount`; an accepted offer consumes one open slot. For headcount=1 the first accept wins and all other pending offers withdraw. For headcount>1 acceptance continues until capacity fills; then withdraw the rest. Lock the parent job and accepting worker. A job becomes ASSIGNED when capacity is full; partially filled requests remain OFFERING while existing assignments may proceed. This interprets “winner” without losing the explicitly required multi-worker capability.
2. Scheduling: explicit shift windows are the Phase 1 execution contract for all four engagement types. HOURLY/DAILY have a single window; FIXED_TERM/MONTHLY have a bounded, validated list plus recurrence metadata/timezone for future generation. No unbounded recurring generation tonight. Every recurring assignment gets multiple Shift rows. UI must collect shift times, not guess 24-hour days. PostgreSQL timestamps are UTC; recurrence metadata keeps IANA timezone.
3. Availability: ONLINE means accepting immediate offers; it is not verification and does not cancel accepted work. Scheduled availability and engagement lists constrain future shifts. Recheck schedule conflicts at acceptance.
4. Verification: operations explicitly approves required IDENTITY and POLICE records; DRIVER also needs DRIVING_LICENSE where configured in service requirements. Worker ACTIVE additionally requires completed onboarding and an explicit authorized activation decision. Approval is never inferred from upload existence. Requirement policy is data/config driven.
5. Quote-on-request is valid. Missing rate is not zero pay. Accepted offers freeze agreed worker earning amount in integer paise; no automatic earnings without confirmed commercial terms. Client payment settlement remains independent.
6. Admin “manual assign” means selecting eligible candidate and sending an offer, followed by worker acceptance. An exceptional forced assignment would require an explicit future policy; do not silently bypass worker consent.
7. Manual attendance: worker requests review with reason; operations approves/rejects with reason. Approval creates MANUAL_CHECK_IN and audit record; original failed observations are preserved. There is no client-side bypass.
8. Complete-shift is atomic and idempotent. It creates at most one earning per shift when amount is agreed; future confirmation/disputes can use COMPLETION_PENDING. Assignment completes after all non-cancelled shifts complete; job completes after fulfillment of all required slots/shifts, including replacements.
9. Release blockers are visible, never faked: production host/DB/storage/email, Apple membership/identifiers/signing, Expo project, official contact/store links, reviewed privacy/terms/worker policy and device verification. Development defaults cannot silently ship.
10. Worker availability setup saves the chosen service area in OFFLINE mode without requiring GPS. Foreground location is required when switching ONLINE or checking in for a shift; switching OFFLINE preserves the last known point without requesting permission. This avoids blocking resumable onboarding on a permission unrelated to the current action.

13. Marketplace Phase 1 (owner decision, 2 Oct 2026). Phase 1 is now the Dehradun blue-collar daily-work marketplace, centred on "काम चाहिए आज?". Employers post a one-day requirement in one step (POST /jobs/quick, DAILY, wage in paise, auto-submitted, nearby eligible workers notified). Workers browse nearby open jobs (2/5/10/20 km, skill, today, minimum wage, daily vs permanent) and tap "मैं उपलब्ध हूँ", which creates a JobInterest. The employer choosing an interested worker creates a normal JobOffer, and the worker still accepts it, so JobRequest, JobOffer, Assignment, Shift and AttendanceEvent stay separate and every existing guard (verification, rate, schedule conflict, headcount, idempotent accept) still applies. This supersedes the earlier "no worker browsing/feed" exclusion for this feed only; chat, subscriptions, referrals and surge pricing remain out of scope. The worker side stays free; employer pricing is not implemented and no prices are shown until the owner confirms them.
14. Catalog and localities. Services are extended with Mason, Carpenter, Painter, Electrician, Plumber, Welder, Helper, Cook, Waiter, Housekeeping, Delivery Worker, AC and Refrigerator Technician, Beautician, Mechanic, Construction Supervisor and Hotel and Resort Staff (database rows, English and Hindi). The new trade categories default to IDENTITY verification only so daily work can start; the household categories keep IDENTITY and POLICE. This is an owner-configurable default, not a policy claim. Localities (ISBT, Patel Nagar, Sahastradhara, Raipur, Clement Town, Prem Nagar, Selaqui, Vikasnagar, Doiwala) are seeded by name only with NULL coordinates because no verified points were supplied; jobs use the employer's GPS point and the locality is a label.
15. Trust score and wage comparison use real data only. Trust is the average of actual reviews with a review count and is empty when there are none. Wage benchmark is computed from real DAILY postings in the last 60 days and returns nothing until at least 5 samples exist.

Permanent jobs reuse MONTHLY and FIXED_TERM requirements.
17. Writing rule (owner, locked): no em dashes anywhere. Enforced by `npm run lint:dash` and the pre-commit hook.
18. Guest browsing before sign-up (owner and client feedback, 3 Oct 2026). The app opens on a public home, not the login screen. Without an account a visitor can browse open jobs and listed workers, filter by service, read About Labour Youth, and switch language. Creating an account is asked only when the visitor acts (apply, hire) or chooses to register. Backend: unauthenticated read-only `GET /public/jobs` and `GET /public/workers`, rate limited per IP. Jobs expose service, locality, engagement type, start time, wage and openings left. Workers appear only when ACTIVE with onboarding COMPLETE (operations-verified) and expose first name, skills, experience, area, availability and real review trust. Contact details, exact coordinates, free-text notes, employer identity and documents are never exposed. Decision 28 later permits opaque resource IDs for public detail navigation. Listings are real data only; with none, the screen shows an honest empty state, not sample cards. Writes, offers, interest and selection still require authentication and the existing authorization. Supersedes the earlier assumption that every screen sits behind login.

21. Hirer WhatsApp and Google Maps link instead of device GPS (owner, 3 Oct 2026). Hirers no longer share device location. Client setup asks for a WhatsApp number (prefilled from the account phone) and an address with an optional Google Maps link; quick post asks for a Maps link. The server reads the pin from the link: typed coordinates, full google.com/maps URLs, and maps.app.goo.gl short links followed hop by hop, contacting only Google Maps hosts (SSRF guard, 5 s timeout, 5 hops). Without a readable pin the job is AREA precision: its point is the service-area centre, the worker feed says "in your area" instead of a distance, and check-in only verifies presence inside the service area. The hirer's WhatsApp number and Maps link unlock for a worker only after the hirer selects that worker (pending or accepted offer, or live assignment), through `GET /jobs/{id}/contact`; listings, the public browse and the nearby feed never include them. The worker then calls or messages the hirer and can ask for the location on WhatsApp. Worker GPS for going online and shift check-in (Decision 10) is unchanged.

Each hue has a darker text shade and a soft tint, on a warm paper background #FBFAF7. Every text and fill pairing passes WCAG AA (measured from 4.55:1 for white on rose up to 13:1). Gradients are limited to soft decorative colour fields, a multicolour brand strip and the hero headline accent. The mobile app keeps Decision 20.
Responsive behaviour uses fluid tokens rather than three fixed device classes. The page gutter, section spacing and type sizes interpolate with clamp(). The content frame widens at 1600 and 2000 px, and the root font size scales up on 2000 px and larger displays. Card grids use intrinsic auto-fit columns or container queries, so components respond to the space they actually have. Tile sets use column counts that avoid orphan rows (1, 2, 3 or 1, 2, 4). On narrow screens long tile rows become swipe rows with the next card peeking. Inline navigation appears from 1080 px, with a labelled drawer below that. The layout respects safe-area insets (viewport-fit=cover), uses 44 px tap targets and keeps reduced-motion handling.
The owner named the work their team arranges most often: house help, baby care and babysitting, plumbers, electricians, carpenters, and drivers for a day or a single trip. These appear as "Most requested". The owner also asked to show placeholder testimonials until real ones arrive. Invented quotes and names are not published because they would read as real customers (Decision 23, checklist item 12). Imagery reuses licensed stock photos already in the repository and the AI-generated scenes from Decision 24, each with a disclosure. Copy describes only the current product. 28. Public app marketplace and deferred authentication (owner, 5 October 2026). The Expo app opens as a browseable marketplace. Visitors can select services, browse open roles and available verified workers, and open safe role and worker details without an account. A user icon remains at the top right and offers login or registration at any time. Authentication is required only when someone applies for a role or requests a worker. The app stores that action through login, registration and any required CLIENT or WORKER onboarding, then continues it automatically.

Public responses may expose opaque listing and profile IDs because detail navigation requires stable identifiers. They may also expose job schedule, stated wage and openings, plus worker first name, services, experience, coarse service area, availability, languages, completed-job count, verification marker and real review summary. They never expose a user ID, full name, phone, email, employer identity, exact coordinates, Maps link, private notes or documents. This narrows and supersedes Decision 18 only where it prohibited every public ID.

Requesting a listed worker does not create a direct assignment. The authenticated hirer completes the normal quick-post fields with the service and preferred worker preselected. The backend creates a JobRequest, rechecks the worker through MatchingService, then creates a PENDING JobOffer. The worker must accept or decline, preserving JobRequest, JobOffer, Assignment, Shift and AttendanceEvent separation.

31. Backend moves from Python/FastAPI to Node.js/Express for Hostinger Cloud hosting (owner, 12 October 2026). The domain stays registered at GoDaddy. The owner wants the website and the backend on Hostinger Cloud hosting, which runs Node.js web apps but not Python, and offers no PostgreSQL. After being shown the cost (a full backend rewrite with its tests) and the VPS alternative, the owner chose the rewrite. Consequences:
- The backend becomes an Express + TypeScript modular monolith in `apps/server`. It keeps the `/api/v1` contract exactly: paths, request and response shapes, status codes and error codes, so the Expo app and the website need no changes. All rules in ARCHITECTURE.md stay in force (Argon2id, rotating refresh tokens with replay revocation, server-side authorization, idempotency, row locks, geofence, audit, outbox).
- The database moves to Supabase PostgreSQL with PostGIS. The schema is unchanged; schema ownership moves from Alembic to plain SQL migrations in `apps/server/migrations`, starting from a baseline taken from Alembic head.
- Private documents move from the local disk to a private Supabase Storage bucket, because Cloud hosting has no safe private disk. The API keeps streaming each file only to an authorized user (owner, reviewer, or a hirer for an assigned worker's photo), so no public or signed URL is handed out and `GET /documents/{id}` is unchanged. The service-role key stays on the server. Staging and production refuse to start without `STORAGE_DRIVER=supabase`; the local-disk driver is for development and tests only.
- Integration tests are rewritten for Node and still run against PostgreSQL/PostGIS, never SQLite.
- The Python backend in `apps/api` stays as the reference until the Node backend passes the ported tests for every module, then it is removed. Until then, `apps/api` remains the running backend.
This supersedes the FastAPI choice in AGENTS.md and ARCHITECTURE.md and the Railway/Supabase/Vercel plan in API_HOSTING.md.
