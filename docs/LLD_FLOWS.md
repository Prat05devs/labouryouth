# End-to-end flows and edge cases
## Bootstrap and auth
1. Restore SecureStore refresh session, obtain access token, call `/me`. Network failure shows retry and never treats cached role as authorization.
2. No session: login/register. Registration validates matching passwords, normalized email/phone, unique constraints; hash password. Choose Hire Staff/Find Work; add CLIENT/WORKER idempotently. Users cannot self-grant admin roles.
3. No roles → purpose selection; incomplete profile → resumable onboarding. One role → its app; two → last permitted mode. Logout clears local secrets and revokes server session. Reset consumes one-use hashed token and revokes all sessions. Expired refresh returns to sign-in.
4. Settings expose language, mode switch, sign-out, password reset and account deletion request with explicit confirmation/reauthentication. Never store passwords or access tokens in analytics.

## Client
Short onboarding saves name/type/primary address. Home loads catalog from API plus own active requests; empty state prompts a requirement. Wizard: service → engagement → validated requirements → bounded shift schedule/headcount → owned address or new location → budget/quote → review → create DRAFT → submit. Failure preserves draft. Service inactive or out-of-area is actionable validation, never silently remapped.
Job detail returns aggregate timeline, offers only as permitted, assigned worker public profile, next shift and replacement/report controls. Address edit cannot change snapshot. Check-in and completion updates are event-driven/pollable. Completed assignments unlock one client review. Cancellation calls explicit action, records actor/reason and pending refund metadata, cancels unused capacity/offers and preserves work/history.

## Worker onboarding and work
Save and validate each named step independently with progress and version. Upload photo and required evidence privately, then associate owner-scoped metadata. Interrupted uploads retry without marking evidence complete. Submit requires required steps/evidence but does not imply verification. Reviewer corrections return relevant step; rejection reason visible without exposing internal notes. Bank details remain a placeholder; do not collect unnecessary sensitive information.
Verified ACTIVE workers choose online/offline; offline does not abandon assigned shifts. Offers show work/location as authorized, time, engagement, agreed earning/quote and expiry. Accept/decline disables duplicate UI actions but relies on server transaction. Expired/withdrawn offer refreshes with clear state; lost race displays JOB_ALREADY_ASSIGNED.
Assigned → Start Journey → EN_ROUTE → I've Arrived → ARRIVED → Start Shift. Request foreground permission only when needed. Send coordinate/accuracy/time plus idempotency key. Validate actor, verification, active assignment/shift, scheduled window, observation age/accuracy and ST_DWithin. Record acceptance/rejection without overwriting history. GPS denied/poor/outside: explain, retry, or request manual review with reason. Do not spoof coordinates or bypass backend checks.
Complete Shift posts authoritative server end event, completion, notification and one earning if terms confirmed. Repeated request returns original outcome. Multiple shifts leave next work available. Earnings are ledger sums by currency; pending/paid distinction never inferred solely from client payment status.

## Matching and operations
Admin role/auth checked on server before loading operations data. Verification queue uses short-lived private document access. Approve/reject requires reason for rejection and audit; activation checks policy. Candidate generation filters service, required verification, eligible worker status, immediate/scheduled availability, area/radius, engagement, rate and conflicts; saves distance/scoring components and generated time. Deterministic ranking only; no AI. Rerun makes prior results stale, not binding commitments.
Operations selects candidate and sends offer with expiry/terms. Worker acceptance rechecks all constraints. Single-slot winner withdraws other offers; multi-headcount fills remaining slots. Worker row locks serialize conflicting offers from different jobs. Scheduler expires pending offers, but accept always enforces expiry inline. Job/assignment details provide operations timeline and exceptional paths.

## Replacement and incidents
Client/assigned worker creates ReplacementRequest with enumerated reason. Enforce ownership and one open request per affected assignment. Admin reviews and starts MatchingService excluding original worker; send replacement offer referencing request/slot. On acceptance create new Assignment with replacement_of_id; preserve original fulfilled shifts and ledger, close future original shifts with reason, create remaining shifts for replacement, mark original REPLACED at handover and resolve request. Declined/expired replacement offer leaves queue open. No staff available → visible ON_HOLD/unresolved reason, never fake assignment.
Incident intake stores reporter/type/details; operations investigates. Visibility limited to involved parties/support as appropriate. No automatic worker punishment from a report. No-show determination requires server-side policy and audited evidence.

## Money, pricing and notifications
PricingService takes service/engagement/duration/headcount/area/client type/subscription context; returns configured rate or quote-required. Quote cannot become zero silently. Freeze agreed job/worker terms before work. Cash/manual UPI pending is not CAPTURED until authorized reconciliation with evidence; payment and worker earnings are independent.
Ledger append with source_key for each earning. Corrections use signed adjustment or linked reversal; no UPDATE/DELETE. Manual payout records amount/status and posts payout entry exactly once; reversal compensates. Payment callbacks are future provider adapter work.
Domain actions write transactional outbox events: JobSubmitted, OfferCreated, OfferAccepted, AssignmentCreated, WorkerEnRoute, WorkerCheckedIn, ShiftCompleted, ReplacementRequested, ReplacementAssigned, PaymentCaptured, PayoutCompleted, VerificationApproved. Idempotent handlers persist localized-key Notification plus route/entity IDs. Push/email delivery failure does not roll back valid domain work and is retried visibly.

## Cross-cutting failure handling
Bound pagination and upload sizes; reject malformed schedule/coordinates/amounts. Unknown IDs and another user's private objects produce safe 404/403 without leaking data. Database constraint conflicts translate to structured errors. Transaction rollback prevents partial assignment/ledger/outbox work. Idempotency records include request hash; key reuse with changed payload conflicts. UTC server time wins over device clock. Admin override requires reason and audit, never a free-form status editor.
