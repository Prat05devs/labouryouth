# State machines
All transitions occur in named service actions inside transactions. Invalid transitions return 409 INVALID_STATE_TRANSITION. Actor/ownership checks happen first. Terminal states do not reopen through generic mutation. Audit overrides have explicit reasons.

| Aggregate | Allowed progression and guard |
|---|---|
| JobRequest | DRAFT → SUBMITTED (owner; valid complete demand); SUBMITTED → MATCHING (operations/candidate generation); MATCHING → OFFERING (offer created); OFFERING → ASSIGNED (capacity filled); ASSIGNED → ACTIVE (first shift starts); ACTIVE → COMPLETED (required shifts/slots satisfied) |
| Job side states | DRAFT/SUBMITTED/MATCHING/OFFERING/ASSIGNED → CANCELLED through cancellation policy; ACTIVE cancellation closes remaining shifts via audited policy, preserving completed work. SUBMITTED/MATCHING/OFFERING → EXPIRED after service window ends. SUBMITTED/MATCHING/OFFERING/ASSIGNED → ON_HOLD with reason and remembered prior state; explicit resume only if still eligible |
| JobOffer | PENDING → ACCEPTED/DECLINED/EXPIRED/WITHDRAWN; ACCEPTED creates exactly one assignment atomically. Expiry checked on every accept even if sweeper has not run. Terminal values immutable |
| Assignment | PENDING → ACCEPTED (offer acceptance normally creates ACCEPTED directly); ACCEPTED → EN_ROUTE → ARRIVED → IN_PROGRESS → COMPLETED; ACCEPTED/EN_ROUTE/ARRIVED → NO_SHOW by audited operations with evidence; live states → CANCELLED under policy; accepted replacement makes original REPLACED; terminal records remain historical |
| Shift | SCHEDULED → IN_PROGRESS (valid check-in or audited manual approval); IN_PROGRESS → COMPLETED tonight; future IN_PROGRESS → COMPLETION_PENDING → COMPLETED/DISPUTED; DISPUTED resolves by explicit audited action. SCHEDULED → CANCELLED/MISSED; no silent check-in of missed/cancelled shift |
| Verification | NOT_SUBMITTED → PENDING on submitted evidence; PENDING → APPROVED/REJECTED by authorized reviewer; APPROVED → EXPIRED when expiry reached or REJECTED after audited revocation; REJECTED/EXPIRED → PENDING on resubmission preserving prior review history |
| Onboarding | NOT_STARTED → IN_PROGRESS on first save; IN_PROGRESS → SUBMITTED after all required steps; SUBMITTED → COMPLETE after approval or IN_PROGRESS with requested corrections. Worker activation is a separate policy check |
| Worker | PENDING_VERIFICATION → ACTIVE only on required approvals+completed onboarding; ACTIVE ↔ INACTIVE by permitted policy; ACTIVE/INACTIVE → SUSPENDED/BLOCKED only authorized reasoned action; reinstatement explicit, never incident-driven automatically |
| Replacement | REQUESTED → UNDER_REVIEW → MATCHING → OFFERING → ASSIGNED → RESOLVED; REQUESTED/UNDER_REVIEW → REJECTED; open request → CANCELLED when no longer needed. Original assignment remains authoritative until replacement is accepted and effective handover recorded |
| Incident | OPEN → UNDER_REVIEW → RESOLVED → CLOSED; reopening by support action with reason. Reporting alone never suspends/penalizes worker |
| Payment | CREATED → PENDING; PENDING → AUTHORIZED/CAPTURED/FAILED; AUTHORIZED → CAPTURED/FAILED; CAPTURED → PARTIALLY_REFUNDED/REFUNDED; PARTIALLY_REFUNDED → PARTIALLY_REFUNDED/REFUNDED with aggregate refund cap. Refund is a new financial event; gateway callbacks later authenticated/idempotent |
| Payout | REQUESTED → APPROVED → PROCESSING → PAID/FAILED; FAILED → PROCESSING via audited retry; PAID → REVERSED via compensating ledger, never editing posted entries |

## Multi-shift and multi-worker aggregation
Each assignment can return to ARRIVED/EN_ROUTE for the next scheduled shift after the previous shift completes; explicit `prepare-next-shift` action moves IN_PROGRESS → ACCEPTED only when no shift remains in progress and future shifts exist. Assignment stays IN_PROGRESS until final completion or this reset; UI chooses upcoming shift action from both assignment and shift state. Do not mark a recurring assignment complete after its first shift.
Partially filled requests stay OFFERING; first active shift may move the job to ACTIVE even before all slots fill. Candidate/offer actions are allowed for remaining capacity while ACTIVE. Completion requires every slot fulfilled or an audited reduction/cancellation of remaining scope. Replacement occupies original slot, never increments headcount.

## Concurrency and invariants
Lock JobRequest then worker before accepting. Recheck job availability, headcount/slot, offer expiry/ownership, verification, services, location/availability, engagement/rate and conflicts. Insert Assignment/shifts, accept offer and withdraw offers only after capacity filled; events and audit in same commit. Winner replay returns same assignment; losing competing acceptance returns 409 JOB_ALREADY_ASSIGNED. Database uniqueness protects live slots and offer→assignment mapping. A blocked/suspended worker cannot begin a shift. Replays cannot create extra shifts, attendance or earnings.
